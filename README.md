# TaskFlow

A small asynchronous task-management API built with FastAPI. It demonstrates Python async I/O,
SQLAlchemy, PostgreSQL, Pydantic, Redis, testing, Docker, and CI in a single runnable project.

## Architecture

```text
HTTP client -> FastAPI -> SQLAlchemy async session -> PostgreSQL
                    \-> Redis (cache for individual task reads)
```

- PostgreSQL is the source of truth; Alembic manages the schema.
- `GET /tasks/{id}` uses a cache-aside strategy. Updates and deletes invalidate the cached item.
- Redis errors are logged and treated as cache misses; writes still use PostgreSQL. Cached values
  expire after `CACHE_TTL_SECONDS` (60 seconds by default). The cache is best-effort: a failed
  invalidation or concurrent read/write can temporarily serve stale data until the TTL expires.
- Database operations and Redis I/O use `async`/`await`. Request validation and serialization use
  Pydantic. API documentation is generated by FastAPI.
- The app is a portfolio demo, not a production-ready multi-user service. It has **no authentication
  or authorization**. Do not expose it to untrusted networks without adding those controls.

## Requirements

- Docker with Docker Compose, or Python 3.12+ and [uv](https://docs.astral.sh/uv/).
- PostgreSQL and Redis, provided by Compose for local development.

## Quick start with Docker

```bash
cp .env.example .env
docker compose up --build
```

The Compose API service applies migrations before it starts. Open <http://localhost:8000/docs>
for the interactive API, or <http://localhost:8000/health> for a liveness check. Stop the stack with
`docker compose down`; its PostgreSQL volume is retained. Compose binds PostgreSQL and Redis only
to localhost, but the API port is exposed on all interfaces by default.

The sample credentials and Redis configuration are **for local development only**. If you change
Compose's PostgreSQL credentials, use URL-safe values. Changing them after the PostgreSQL volume
has been initialized does not change the credentials already stored in that volume.

## Local development with uv

Start PostgreSQL and Redis (or provide your own instances), then run the app:

```bash
cp .env.example .env
docker compose up -d postgres redis
uv sync --frozen
uv run alembic upgrade head
uv run uvicorn taskflow.main:app --reload
```

Configure the app through environment variables or `.env`:

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | `postgresql+asyncpg://taskflow:taskflow@localhost:5432/taskflow` | Async SQLAlchemy connection URL |
| `REDIS_URL` | `redis://localhost:6379/0` | Redis connection URL |
| `CACHE_TTL_SECONDS` | `60` | Positive cache lifetime in seconds |

Values in `.env` are examples, not production secrets. Environment variables take precedence over
the file. `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_DB` configure the Compose database;
for local non-Compose Python processes, update `DATABASE_URL` separately to match them.

## API examples

Create a task:

```bash
curl -X POST http://localhost:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Write tests","description":"Cover the task API"}'
```

List and filter tasks, retrieve one, update it, or delete it:

```bash
curl 'http://localhost:8000/tasks?status=todo&limit=20&offset=0'
curl http://localhost:8000/tasks/1
curl -X PATCH http://localhost:8000/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"status":"done"}'
curl -X DELETE http://localhost:8000/tasks/1
```

Statuses are `todo`, `in_progress`, and `done`. Titles are trimmed and must contain 1–200
characters. `PATCH` accepts partial updates; `description` may be set to `null`, but `title` and
`status` may not. Missing tasks return 404, invalid requests return 422, and successful deletion
returns 204. Lists are ordered by ID and support `limit` (1–100) and non-negative `offset`.

For example, the SQL equivalent of a filtered list is:

```sql
SELECT id, title, description, status, created_at, updated_at
FROM tasks
WHERE status = 'todo'
ORDER BY id
LIMIT 20 OFFSET 0;
```

## Tests and quality checks

```bash
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
```

By default, API tests use an in-memory SQLite database and a Redis test double. Migration tests
use a temporary SQLite database and exercise both upgrade and downgrade. To also run API tests
against PostgreSQL and the Redis integration test against Redis:

```bash
TEST_DATABASE_URL='postgresql+asyncpg://taskflow:taskflow@localhost:5432/taskflow' \
TEST_REDIS_URL='redis://localhost:6379/0' uv run pytest -q
```

PostgreSQL tests create and remove randomly named `test_*` schemas, so the database user needs
permission to create schemas. Redis integration tests create and remove a randomly named task key.
Use dedicated test services. The optional Redis test is skipped when `TEST_REDIS_URL` is unset.
GitHub Actions runs linting, migration upgrade/downgrade, tests with PostgreSQL and Redis, and a
Docker build.

## Deployment notes

The container can be deployed to a service such as AWS ECS or another container platform, but no
cloud infrastructure or deployment has been provisioned in this repository. For a real deployment,
use managed PostgreSQL and Redis, private networking, TLS, a secrets manager, authentication,
monitoring, backups, and appropriately configured database connection limits. Run Alembic as a
controlled deployment step instead of allowing multiple replicas to migrate concurrently. `/health`
is a liveness endpoint and does not check database or Redis readiness.

## Publish to GitHub

Create an empty repository on GitHub, then add its URL and push the existing `main` branch:

```bash
git remote add origin https://github.com/YOUR_USERNAME/task-flow.git
git push -u origin main
```

Do not commit `.env` or real credentials.
